# 第 7 章　投机解码

先回答一个问题：**为什么 decode 慢？** 第 0.5 节讲过——decode 是「一步一个 token」的串行过程，每生成一个 token 都要把整个模型权重从显存读一遍，算力在旁边干等数据（访存墙）。投机解码的聪明之处在于：不搬更多数据，而是让**同样的一次权重读取产出更多 token**。

## 7.1 原理：draft + verify，为什么能突破访存墙

![draft 先猜、主模型并行验证：一次前向换来多个 token](./assets/ch07-draft-verify.png)

第 1.3 节讲过：**Decode 是 Memory-bandwidth-bound**——常规 decode 里读一次权重只换 1 个 token，这就是「访存墙」的字面意思。

投机解码（注意：是「投机」，不是「推测」）分三步：

1. **Draft（起草）**：用一个**廉价得多**的模块快速「猜」出后续 `k` 个候选 token（小模型、轻量 head、N-gram）。
2. **Verify（验证）**：把「原序列 + `k` 个候选」拼成长度 `k+1` 的序列，**主模型一次前向并行验证**所有位置。
3. **接受/回退**：从前往后比对主模型真实分布与草稿分布，第一个不一致处截断，接受之前所有一致的 token。

关键在第 2 步：**验证 `k` 个 token 只需要一次前向，而这一次前向的代价，原本只够主模型产出 1 个 token。** 单位权重读取产出的 token 数变多了——这就直接攻击了访存墙；省下的不是计算，是「读权重的次数」。

一个重要的性质：**验证过的输出和逐步解码在分布上等价**。草稿错了会被主模型拒绝、在拒绝处回退，所以投机解码是「无损加速」——改变的是生成效率，不改变输出分布。这也是它和量化（有精度代价）最大的区别。

## 7.2 方案全景：六种方案与选型

### 7.2.1 六种方案一张表

| 方案 | draft 来源 | 额外显存/算力 | 接受率特征 | 适用场景 | 主要代价 |
|---|---|---|---|---|---|
| **N-gram** | 请求自身历史的 n 元组统计，无需模型 | 几乎为零 | 模板化/重复文本高，自由生成低 | 代码补全、模板、重复结构输出 | 对开放式生成几乎无效 |
| **Draft Model** | 一个更小的独立模型 | 需额外权重显存 + draft 算力 | 取决于小模型与目标模型分布接近度 | 有现成小模型、分布接近 | draft 太慢或分布偏则劣化 |
| **EAGLE / EAGLE3** | 在目标模型隐藏态上训练一个轻量自回归 head | 较小（head 参数少），需训练好的 draft 权重 | 高（head 显式拟合目标分布） | 通用对话、分布多样的生成 | 需要对应模型的 draft 权重，并非所有模型都有 |
| **MTP**（Multi-Token Prediction） | 模型自身带的「多 token 预测」层（如 DeepSeek） | 极小（复用主模型层） | 高（与主模型同源） | DeepSeek 等原生支持 MTP 的模型 | 仅限模型架构支持 |
| **DFlash** | 独立的**块扩散（block diffusion）**草稿模型，一次前向并行起草整块 token | 小（如 5 层、约 1GB 级草稿权重） | 高且稳（并行起草不随块长衰减，代码等可预测负载收益最大） | 有配套 DFlash 草稿的模型；代码生成、批量抽取 | 需专门训练的 DFlash 草稿权重，与目标模型绑定 |
| **DSpark** | DFlash 骨架 + **顺序修正 + 置信度头**（草稿先自评分，只送高置信候选去验证） | 小（同 DFlash 量级） | 更高（过滤低质量草稿，等效接受数再升，还省验证算力） | 高吞吐 decode、长输出、新架构模型（混合线性注意力等） | 同 DFlash；配置项更多，需确认配套权重 |

> 注意：DFlash / DSpark 并非所有模型都有配套草稿权重，动手前先到 HuggingFace 搜「<模型名>-DFlash / -DSpark」确认。它们在 vLLM（经 Speculators 生态）与 SGLang（原生支持）都已可用。

### 7.2.2 双引擎配置对照

vLLM V1 通过统一的 `--speculative-config`（一个 JSON 块）配置不同方法；SGLang 通过 Spec V2 框架（算法 + 草稿路径分开传参）。

```bash
# ── vLLM（V1 引擎，v0.20.x–v0.21.x；键名与取值以版本文档为准）──

# N-gram：零成本，先试这个最稳
vllm serve Qwen/Qwen3-8B-Instruct \
  --speculative-config '{"method": "ngram", "num_speculative_tokens": 5}' \
  --gpu-memory-utilization 0.90

# EAGLE：需要对应模型的 draft 权重路径
vllm serve Qwen/Qwen3-8B-Instruct \
  --speculative-config '{"method": "eagle", "model": "<eagle-draft-path>", "num_speculative_tokens": 5}' \
  --gpu-memory-utilization 0.90

# MTP（DeepSeek 等原生支持）：model 指向主模型，由引擎加载 mtp 层
vllm serve deepseek-ai/DeepSeek-V3 \
  --speculative-config '{"method": "mtp", "model": "deepseek-ai/DeepSeek-V3", "num_speculative_tokens": 4}' \
  --tensor-parallel-size 8

# DFlash：需要配套的 DFlash 草稿权重（示意，method 名以版本文档为准）
vllm serve Qwen/Qwen3.5-27B \
  --speculative-config '{"method": "dflash", "model": "z-lab/Qwen3.5-27B-DFlash", "num_speculative_tokens": 15}' \
  --gpu-memory-utilization 0.90

# ── SGLang（v0.5.18+，Spec V2）──

# EAGLE 草稿（需对应的 eagle 权重）
python -m sglang.launch_server \
  --model-path Qwen/Qwen3-32B \
  --tp 4 \
  --speculative-algorithm EAGLE \
  --speculative-draft /path/to/eagle-qwen3-32b \
  --speculative-num-steps 4                          # 每次猜几步

# MTP 草稿（DeepSeek 等原生带 MTP head 的模型）
python -m sglang.launch_server \
  --model-path deepseek-ai/DeepSeek-V3 \
  --tp 8 \
  --speculative-algorithm MTP \
  --speculative-num-steps 3

# DFlash 草稿（并行起草，需配套草稿权重；示意键名以官方文档为准）
python -m sglang.launch_server \
  --model-path Qwen/Qwen3.5-35B-A3B \
  --tp 1 \
  --speculative-algorithm DFLASH \
  --speculative-draft-model-path z-lab/Qwen3.5-35B-A3B-DFlash \
  --speculative-num-draft-tokens 16                  # 一次起草一整块
```

> 两个引擎的参数语义差异要注意：vLLM 的 `num_speculative_tokens` 与 SGLang 的 `--speculative-num-steps` 都偏「自回归起草的步数/链长」语义；而 SGLang 的 `--speculative-num-draft-tokens` 是**整块大小**——并行起草与自回归起草的参数语义不同，不是「串行猜几步」。

**判断（不下「谁更好」）**：两者能用的草稿方法高度重叠，单看速度没有谁碾压谁。SGLang 的优势是「前缀缓存 + 投机解码」能同时开（多轮 Agent、批量抽取收益叠加），vLLM 的优势是已是 vLLM 服务时省迁移。

## 7.3 专题：从「自回归起草」到「并行起草」（DFlash / DSpark） ★★★ ⏭️

五类方案（N-gram / Draft Model / EAGLE / MTP）共享同一个隐藏假设：**草稿是一个一个 token 串行猜出来的**——EAGLE-3 再强，猜 5 个候选也要跑 5 步 draft 前向。于是草稿模型不能做大（起草成本随链长线性涨），`num_speculative_tokens` 也敏感。

**并行起草（parallel drafting）把这个假设干掉了**：起草从「循环 k 次」变成「一次前向出整块」，耗时与块长解耦——草稿可以更大更准，块长不再是需要精调的参数。**工程视角的两个判断**：

1. **受益最大的是代码与结构化文本负载**。社区实测里代码场景单步接受 6–7 个 token 并不罕见，自由散文则明显低。
2. **验证侧成了新瓶颈**。起草变便宜后，成本重心移向「验证一堆最终会被拒绝的候选」——DSpark 的置信度头就是冲这个来的。

## 7.4 接受率（acceptance rate）怎么看，多少算好

![草稿模型快速猜、主模型并行验证；猜中的接受，猜错的拒绝](./assets/ch07-speculation-speedup.png)

两个引擎都会暴露接受指标（`num_accepted_tokens / num_drafted_tokens` 之比，以及每步平均接受的 draft token 数）。读法：

- **有效接受 token 数** ≈ `链长 × 接受率`。比如配了 5 个、接受率 0.6，等效每步白赚约 3 个 token。
- **没有绝对阈值**。N-gram 在模板代码上可以很高，开放创作上可能趋近 0；EAGLE 遇到分布偏移也会掉。
- **判据是相对的**：对照「不开投机解码」的 TPOT，等效每步接受 token 数 ≳ 1 且 TPOT 下降就是赚；等效接受 ≈ 0 时，draft + verify 的开销就是纯亏。

**接受率与链长的数学关系**。设每位置被独立接受的概率为 `p`，则「前 `i` 个候选全对、第 `i+1` 个错」的概率是 `p^i · (1−p)`，等效每步接受的 token 期望 ≈ `Σ p^i`（从 i=1 到链长）。当 `p=0.6`、链长 5 时，期望 ≈ 0.6+0.36+0.216+0.13+0.078 ≈ 1.38；把链长加到 10，期望 ≈ 1.48——**几乎没涨**：越往后 `p^i` 衰减越快，而 draft 成本与 verify 长度线性增加。**链长的甜区通常就在 3–5，超过后边际收益断崖。** 真正的杠杆在「提高 `p`」（选对 draft），而不是「加长链」。

## 7.5 陷阱：draft 选错反而劣化延迟

1. **draft 比 verify 还慢**（最常见）。draft 模型太大、或路径没优化好，其耗时接近甚至超过「主模型多跑几步」，延迟不降反升。N-gram 之所以安全，正因为它几乎零成本——**先用 N-gram 探路就是为避免这个坑。**
2. **draft 与 target 分布差距大 → 接受率崩盘**。配了 5 个候选平均只接受 0.2 个：draft 白算、verify 也跑，等效只多产出 0.2 个 token，**开销照付，收益近乎零**。用通用小模型去 draft 专业领域大模型时极易发生。
3. **结构化输出 / 约束解码场景**。decode 被 JSON Schema / Regex 约束时（见 9.3 节），draft 候选常落在约束外被整体拒绝，接受率断崖式下跌；vLLM 与 xgrammar 有专门路径，但这类负载仍要特别谨慎。
4. **链长配太大**。「前面全对」才接受，链越长整条被拒的概率指数上升，长链 + 低接受率 = 大量「白 draft」。**一般从 3–5 起步扫描。**
5. **两端收益都小**。小 batch 时访存墙不尖锐，大 batch 时 decode 已接近 compute-bound。最甜的区间是中低并发、访存受限的 decode。

> **反模式小结（本章）**：① 直接上 EAGLE 却没先验证 draft 权重匹配；② 接受率没看就宣布「投机有效」；③ 结构化输出场景无脑开投机；④ 链长设很大以为更赚。

## 7.6 动手实验：EAGLE vs N-gram 实测对比

配套仓库 `src/ch07-speculative/spec_decode_bench.sh` 在同一模型、同一负载上分别用 N-gram 与 EAGLE 启动，跑同一组 `vllm bench serve`，抓 TPOT P99、吞吐与接受率。

```bash
# spec_decode_bench.sh（节选，详见仓库 README）
# 1) 基线：不开投机
vllm serve Qwen/Qwen3-8B-Instruct --port 8000 --gpu-memory-utilization 0.90 &
run_bench_and_save base.json

# 2) N-gram
vllm serve Qwen/Qwen3-8B-Instruct --port 8001 \
  --speculative-config '{"method":"ngram","num_speculative_tokens":5}' &
run_bench_and_save ngram.json

# 3) EAGLE（需 draft 权重）
vllm serve Qwen/Qwen3-8B-Instruct --port 8002 \
  --speculative-config '{"method":"eagle","model":"<eagle-draft-path>","num_speculative_tokens":5}' &
run_bench_and_save eagle.json
```

**预期判读**：模板化/重复负载上 N-gram 可能已接近 EAGLE；若 EAGLE 的 TPOT 反而更高，先查接受率——多半是 draft 权重不匹配或链长过大。

> **什么场景值得用 / 不值得用**
> - 值得：decode 受限的短输入长输出负载（代码生成、长文写作、批量抽取），且已有高质量草稿（EAGLE/MTP/DFlash/DSpark 权重）。
> - 不值得：prefill 受限的长 prompt 短输出（投机帮不上 prefill 的忙）；草稿模型与主模型分布差太远（等效接受数 <1.5 时基本亏）。

## 本章小结

1. **投机解码 = draft（廉价起草）+ verify（一次前向整块验证）**，把「读一次权重产 1 token」升级为「产 k 个」，直接攻击 decode 访存墙；验证分布等价、无损加速。
2. **方案选型按「手头有什么」**：有 MTP 用 MTP，有 EAGLE 权重用 EAGLE，有配套 DFlash/DSpark 优先并行起草，都没有先用 N-gram 探路——它零成本，永远是第一步。
3. **接受率是生命线**：有效接受 token 数 ≈ 链长 × 接受率；链长甜区 3–5，加长的边际收益指数衰减（p=0.6 时从 5 加到 10 期望只从 1.38 到 1.48）；杠杆是提高 p。
4. **最甜的区间是中低并发、访存受限的 decode**：上线前先 N-gram 探路确认链路通 → 对照基线 TPOT 确认真变快 → 接受率有监控再常开；结构化输出必须先实测接受率。
