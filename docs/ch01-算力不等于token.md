# 第 1 章　算力 ≠ token：从裸卡到可用服务

## 1.1 从 `transformers.generate` 到推理引擎

一个能跑的服务，和一个能用的服务

几乎所有人都从这段代码开始：

```python
from transformers import AutoModelForCausalLM, AutoTokenizer

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-8B", device_map="cuda")
outputs = model.generate(**tokenizer(prompt, return_tensors="pt").to("cuda"),
                         max_new_tokens=256)
print(tokenizer.decode(outputs[0]))
```

本地跑得很顺。于是把它包一层 FastAPI 就上线了。然后就会遇到三个问题，一个比一个致命。

**问题一：串行处理，GPU 大部分时间在发呆**

`generate()` 一次处理一个请求。真实服务里请求是并发来的，但这段代码让它们排队。

更要命的是，单个请求也未必能吃满 GPU。第 1.3 节会说明为什么：decode 阶段每步只生成 1 个 token，算术强度极低，GPU 的算力单元基本闲置，全在等数据从显存搬过来。

**问题二：显存按最坏情况预留**

朴素实现（旧版静态 KV 分配）通常按 max_length 一次性给 KV Cache 预留连续显存。请求实际生成 200 个 token，系统却按 2048 预留。 多出来的显存既不能被其他请求用，也不能提高批大小 —— 纯粹的浪费。

**问题三：没有调度，就没有 SLO**

SLO（Service Level Objective，服务等级目标）是业务方对服务质量定下的量化目标：多快、多稳定才算达标？比如P99 延迟 < 2 秒、TTFT < 500ms、可用性 99.9%。它把「快、慢、稳不稳」这种模糊的感受，翻译成一行能测量的数字。

这个数字是面向每个请求的承诺。而一个请求在系统里怎么排队、谁先谁后、会不会被长请求饿死、显存不够时怎么办——全由调度决定。请求无法抢占、无法排队管理、显存不够直接 OOM，系统连「P99 延迟是多少」都答不上来，更谈不上守住它。没有调度，就没有 SLO。

手写批处理能解决吗

有人会说：那我自己攒 batch 不就行了？

能解决一部分，但会撞上另一堵墙：

```python
# 手写批处理的典型困境
batch = collect_requests(timeout=50ms)   # 攒够了就跑
outputs = model.generate(**padded_batch)  # 短请求必须 padding 到最长
```

| 困境             | 说明                        |
| -------------- | ------------------------- |
| **Padding 浪费** | 短请求要补齐到 batch 内最长，算力白花    |
| **队头阻塞**       | 一个长请求没结束，同批其他请求已完成也无法释放槽位 |
| **显存仍按最大预留**   | 批处理没解决显存管理问题              |
| **新请求进不来**     | 批次锁死，必须等整批结束              |

本质上，批处理解决的是「GPU 利用率」，而推理引擎解决的是「GPU 利用率 + 显存管理 + 请求调度」三件事。手写批处理只做了第一件。

## 1.2 核心指标体系

### 1.2.1 五个必须分清的指标

在实际的业务需求中，我们需要一些指标来衡量Token，是不是“好用”

| 指标       | 全称                    | 定义                   | 主要由什么决定                    |
| -------- | --------------------- | -------------------- | -------------------------- |
| **TTFT** | Time To First Token   | 发出请求到收到第一个 token 的时间 | Prefill 耗时 + 排队时间          |
| **TPOT** | Time Per Output Token | 生成阶段每个输出 token 的平均间隔 | Decode 单步耗时                |
| **ITL**  | Inter-Token Latency   | 相邻两个 token 的实际间隔     | 同 TPOT，但按逐个 token 统计，能看出抖动 |
| **E2E**  | End-to-End Latency    | 从发出请求到收到最后一个 token   | `TTFT + TPOT × 输出 token 数` |
| **吞吐**   | Throughput            | 单位时间完成的请求数或 token 数  | 与并发、批处理策略强相关               |

![五个指标的时间轴：TTFT、ITL、TPOT、E2E 分别量的是请求时间轴上的哪一段，以及四张指标卡与吞吐的分工](./assets/ch01-metrics-timeline.png)

通过仔细观察我们不难发现这个关系：

```
E2E 延迟 = TTFT + TPOT × (输出 token 数 - 1)
```

它解释了一个常见困惑：为什么长输出的任务，优化 TTFT 没什么用？ 因为输出 2000 token 时，E2E 里 TPOT 的贡献占了绝大部分。

反过来，RAG 场景输入长、输出短，TTFT 才是主要矛盾。

不同场景要优化不同的指标。

### 1.2.2 吞吐有两种算法，别搞混

| 口径           | 单位         | 适用场景        |
| ------------ | ---------- | ----------- |
| **请求吞吐**     | requests/s | 面向终端用户的在线服务 |
| **Token 吞吐** | tokens/s   | 批处理、离线任务    |

Token 吞吐还要区分**输入 token** 和**输出 token**——它们的计算代价完全不同（prefill 是并行的，decode 是串行的）。

### 1.2.3 Goodput：真正该追的指标

先想一家奶茶店。店员手速很快，一小时能做 100 杯，但出杯要 15 分钟，顾客多半等不了，一半人直接走人。这时你说这家店一小时能做 100 杯——有用的吗？做出来的 100 杯里，有 50 杯没送到顾客手里，白做了。

吞吐数的是 `做完了多少`，Goodput 数的是 `送到顾客手里、且顾客还觉得合格的有多少`。超时的请求，对系统来说确实完成了，对业务来说约等于没处理。

回到压测。设 SLO 为 `E2E 延迟 < 2 秒`：

| 并发数 | 吞吐（req/s） | 满足 SLO 的比例 |
| --- | --------- | ---------- |
| 16  | 8.2       | 100%       |
| 64  | 19.5      | 87%        |
| 128 | 24.1      | 41%        |

128 并发时吞吐最高（24.1 req/s），但只有 41% 的请求在 2 秒内返回，剩下 59% 全超时。这些超时请求计进了吞吐，但到用户那里约等于失败。

把两者乘起来，才是真正有效的产出：

**Goodput = 吞吐 × 满足 SLO 的比例**

| 并发数 | 吞吐   | 达标比例 | Goodput   |
| --- | ---- | ---- | --------- |
| 16  | 8.2  | 100% | 8.2       |
| 64  | 19.5 | 87%  | 17.0 ← 最高 |
| 128 | 24.1 | 41%  | 9.9       |

按吞吐选最优是 128，按 Goodput 选最优是 64。系统真正能用的产出在 64 并发时最大——这就是第 0.7 节挑战三「请求不可预测下的 SLO 保障」说的那个拐点。

很多线上事故的根因，就是盯着吞吐调优，一路把并发推过去。监控上吞吐曲线一路向上，用户侧却在疯狂超时——因为超时的请求计入了吞吐，却不算 Goodput。

## 1.3 Prefill 与 Decode：两个阶段，两种瓶颈

![Prefill 与 Decode 两个阶段、两种瓶颈：算术强度、对照表与两阶段混跑的互相伤害](./assets/ch01-prefill-vs-decode.png)

### 1.3.1 两个阶段在做什么

**Prefill（预填充）——像看书。** 拿到完整 prompt 后，模型一口气把**所有**输入 token 同时读进去、并行算完，然后吐出第一个输出 token。整个过程只需要一次前向，输入 100 个 token 和输入 1000 个 token，都是「一遍扫完」，只是内容更多、算得更久。做完这一步，prompt 的 KV Cache 也顺手填好了。

**Decode（解码）——像逐字写字。** 之后 token 是一个一个蹦出来的：这一秒算出第 1 个，下一秒把第 1 个拼回上下文再算出第 2 个，再下一秒算第 3 个……**每算一个，都要把前面所有的字重新看一遍**，所以每步只有一次前向、只产出 1 个 token，且第 t 个 token 依赖第 t-1 个，没法并行。

一句话概括两者的差别：

- Prefill：**一次前向，处理全部输入，并行度拉满**
- Decode：**一次前向，只出 1 个输出，串行推进**

### 1.3.2 为什么一个是算力瓶颈、一个是带宽瓶颈

关键在于**算术强度**（Arithmetic Intensity）——每读取 1 字节数据能做多少次浮点运算。

**Decode 阶段（batch = 1）**

生成一个 token 时：

- 需要读取：全部模型权重（设参数量为 P，BF16 则约 `2P` 字节）
- 需要计算：约 `2P` FLOPs（每个参数约 2 次运算）

```
算术强度 = 2P FLOPs / 2P bytes ≈ 1 FLOP/byte
```

而 H100 的机器平衡点大约是：

```
989 TFLOPS ÷ 3.35 TB/s ≈ 295 FLOP/byte   （以官方规格为准，量级参考）
```

**算术强度 1 远远低于 295。** 这意味着 decode 时 GPU 的算力单元几乎全在空转，时间都花在等权重从 HBM 搬进来。

**Prefill 阶段（输入 n 个 token）**

一次前向处理 n 个 token：

- 读取：模型权重 `2P` 字节（一次读入，服务 n 个 token）
- 计算：约 `2P × n` FLOPs

```
算术强度 ≈ 2P×n / 2P = n FLOP/byte
```

**算术强度随输入长度线性增长。** 输入 512 token 时算术强度 ≈ 512，已经远超 295 的平衡点——**算力打满，带宽反而有余**。这是典型的 compute-bound。

### 1.3.3 一张对照表记住全部差异

| 维度           | Prefill           | Decode                     |
| ------------ | ----------------- | -------------------------- |
| 处理对象         | 全部输入 token（并行）    | 每次 1 个 token（串行）           |
| 瓶颈类型         | **Compute-bound** | **Memory-bandwidth-bound** |
| 算术强度         | ≈ 输入长度（高）         | ≈ batch size（低）            |
| 主导指标         | **TTFT**          | **TPOT / ITL**             |
| 加大 batch 的效果 | 收益有限（已算力饱和）       | **收益显著**（摊薄权重读取成本）         |
| 优化方向         | 分块、稀疏化、前缀复用       | 增大 batch、投机解码、量化、KV 压缩     |

### 1.3.4 推论：为什么加大 batch 能提吞吐

Decode 的算术强度 ≈ batch size。当 batch 从 1 增到 64：

- 读取的权重数据量**不变**（还是那份模型）
- 服务的 token 数变成 64 倍
- 算术强度从 1 升到 64

**一次权重读取，服务了 64 个 token。** 这就是 batch 是吞吐第一杠杆的原因。

但这条路上限明显：

1. **显存上限**：batch 越大，KV Cache 占用越多（第 1.4 节算这笔账）
2. **延迟代价**：batch 大了，单请求等待时间变长——又回到 1.4.3 节的 Goodput 拐点
3. **收益递减**：算术强度超过机器平衡点（~295）后再加 batch，算力已经饱和，只剩延迟在涨

### 1.3.5 推论：为什么两阶段混在一起会互相伤害

把 Prefill 和 Decode 放在同一组 GPU 上：

- 一个长 prompt 请求的 prefill 会占用大量算力，正在进行的 decode 被挤到后面 → **TPOT 尖刺**
- 为了控制 TPOT 而限制 prefill 的算力占用 → **TTFT 变差**
- 两者的最优 batch size、最优并行策略都不一样，只能折中

**这个矛盾没法在单机内彻底解决，只能缓解**（Chunked Prefill，第 5 章）**或绕过**（PD 分离，第 13 章）。

## 1.4 显存账本：显存都去哪了

![显存账本：24GB 的卡真正能用的有多少——四笔账、24GB→8.5GB 的分解与 15 并发的算法](./assets/ch01-memory-ledger.png)

### 1.4.1 四笔账

一张卡的显存被四样东西分掉：

| 占用项          | 说明                      | 是否可压缩        |
| ------------ | ----------------------- | ------------ |
| **模型权重**     | 参数量 × 每参数字节数            | 可以（量化）       |
| **KV Cache** | 所有并发请求的 KV，随并发数和序列长度增长  | 可以（量化、压缩、卸载） |
| **激活值**      | 前向计算的中间结果               | 空间不大，通常不是瓶颈  |
| **碎片与预留**    | 分配器碎片、CUDA context、框架预留 | 可以（分页管理）     |

### 1.4.2 算一笔具体的账

**「7B 模型 BF16 只要 14GB，为什么 24GB 的卡跑起来还是紧张？」**

先别急着怀疑。24GB 减 14GB，还剩 10GB，听起来很宽裕。但这 10GB 不是白给你的：

```
权重：  7B × 2 bytes              = 14.0 GB
CUDA context + 框架预留           ≈ 1.5 GB
─────────────────────────────────────────
真正能用来放 KV Cache 的          ≈ 8.5 GB
```

留意那个 1.5GB——CUDA context、框架那些看不到的开销，先吃掉一小口。**真正给 KV Cache 的只有 8.5GB。**

现在看这 8.5GB 能撑起多少并发。以单个请求、4096 个 token 算（Llama-3.1-8B，32 层、8 个 KV head、head_dim 128、BF16）：

```
KV_bytes = 2 × 32 × 8 × 128 × 4096 × 2 ≈ 536 MB / 请求
```

**一个请求就占 536MB。** 那 8.5GB 能放几个？

```
8.5 GB ÷ 0.536 GB ≈ 15 个请求
```

**所以答案不是「10GB 够用」，而是「8.5GB 只能同时塞下 15 个请求」。** 这就是第前面说的「batch 有显存上限」——不是理论上的上限，是算得出来的上限。

这也顺手解释了几件事：

- 长上下文场景并发数为什么掉得这么狠：上下文翻倍，KV Cache 就翻倍，而算力没变
- 量化为什么这么受欢迎：权重省下的那部分显存，是实打实多出来的并发数
- PagedAttention 为什么价值这么大：把碎片和预留的浪费抠出来，就是白捡的并发

### 1.4.3 一个重要提醒：别把显存用满

`gpu-memory-utilization` 不是越大越好。留出的余量要应付：

- 峰值激活值（长序列、大 batch 时突增）
- 内存分配器的碎片
- 多模态输入、超长 prompt 等意外情况

**用满显存的直接后果是 OOM 崩溃，而不是「略微变慢」**。第 10.2 节会详细讲这个值该怎么设。

### 1.4.4 动手：显存计算器

配套脚本 `src/ch01-foundations/memory_calculator.py` 把上面的计算自动化：

```python
def kv_bytes_per_token(layers, kv_heads, head_dim, dtype_bytes=2):
    """每个 token 的 KV Cache 字节数（K 和 V 各一份）"""
    return 2 * layers * kv_heads * head_dim * dtype_bytes

def max_concurrency(total_gb, weight_gb, reserve_gb, seq_len, per_token_bytes):
    """反推最大并发数"""
    usable = (total_gb - weight_gb - reserve_gb) * 1024**3
    return int(usable // (per_token_bytes * seq_len))

# 示例：Llama-3.1-8B，4096 上下文，24GB 显卡
per_tok = kv_bytes_per_token(layers=32, kv_heads=8, head_dim=128)
print(f"每 token KV：{per_tok / 1024:.1f} KB")
print(f"最大并发：{max_concurrency(24, 16, 1.5, 4096, per_tok)}")
```

## 1.5 推理引擎生态全景

### 1.5.1 主要玩家与生态位

| 引擎               | 维护方                         | 核心优势                                            | 适合谁                          |
| ---------------- | --------------------------- | ----------------------------------------------- | ---------------------------- |
| **vLLM**         | vLLM 社区（PyTorch Foundation） | 模型与硬件覆盖最广、生态最成熟、社区最大                            | 通用场景首选，尤其硬件/模型种类多时           |
| **SGLang**       | LMSYS                       | RadixAttention 前缀复用、结构化输出、前沿模型 Day-0、RL rollout | 重前缀复用场景（多轮/RAG/Agent）、追求前沿特性 |
| **TensorRT-LLM** | NVIDIA                      | 在 NVIDIA 硬件上的极限优化                               | 纯 NVIDIA 环境、愿意投入编译成本换极致延迟    |

| **TGI**          | HuggingFace                 | 部署简单                                            | 已进入维护模式，新项目不建议               |
| **Ollama**       | Ollama                      | 极简本地运行                                          | 本地开发、个人使用，不用于生产              |

### 1.5.2 为什么本项目聚焦 vLLM 和 SGLang

三个理由：

1. **覆盖了绝大多数生产场景。** 这两家是当前开源推理的事实双雄，全球部署量级最大。
2. **代表了两条不同的优化路线。** vLLM 从显存管理切入（PagedAttention），SGLang 从请求复用切入（RadixAttention）。把它们都讲透，读者得到的是完整的优化思维，而不是某个工具的使用手册。
3. **它们的能力大量重叠，选型需要判断力。** 二者都在补齐对方的能力，简单说「谁更快」没有意义。**第 14.1 节会专门做深度对比，给出按场景的选型建议。**

### 1.5.3 一个选型上的提醒

引擎之间的迁移成本比想象中低——因为它们都提供 OpenAI 兼容 API。**换个 `base_url` 就能切换。** 真正在迁移时需要重写的，是引擎特有的能力（DSL、Engine API、特定的投机解码配置）。

所以不用在选型上过度纠结。先选定一个跑起来，用真实负载压测，再决定是否切换——这个顺序比事先反复比较更有效。

## 本章小结


1. **朴素 `generate()` 上线会崩的三个原因**：串行处理导致 GPU 空转、显存按最坏情况预留、没有调度就无法谈 SLO。手写批处理只解决了 GPU 利用率，没解决显存管理和请求调度。
2. **五个指标的分工**：TTFT 由 prefill 决定，TPOT 由 decode 决定，`E2E ≈ TTFT + TPOT × 输出长度`。RAG 类场景主攻 TTFT，长生成场景主攻 TPOT。
3. **Goodput 才是目标函数**。吞吐 × SLO 达成率，才是真正有效的产出。盯着吞吐调优会把服务推过拐点——这是很多线上事故的根因。
4. **Prefill 与 Decode 是两种计算**：Prefill 并行、compute-bound、算术强度≈输入长度；Decode 串行、memory-bound、算术强度≈batch size。**这个区分是全书的第一性原理。**
5. **加大 batch 是吞吐第一杠杆**，因为它摊薄了权重读取成本；但受限于显存（KV Cache 线性增长）和延迟（Goodput 拐点）。


6. **显存四笔账**：权重、KV Cache、激活、碎片预留。8B 模型在 24GB 卡上、4K 上下文，大约只能并发 15 个请求——这是理解很多取舍的数值基础。

7. **方法论四步**：定 SLO → 建基线 → 单点变量 → 回归验证。三个反模式是抄参数、同时改多个变量、只看均值和吞吐。
