## 13.1 为什么需要 PD 分离

### 13.1.1 回到第 1.3 节

第 1.3 节已经确立：**Prefill 是 compute-bound，Decode 是 memory-bandwidth-bound。** 两者的最优资源配比完全不同。

把这两种性格的计算放在同一组 GPU 上，会有三种具体的伤害。

### 13.1.2 伤害一：Prefill 卡住 Decode

一个长 prompt 请求（比如 32K token 的 RAG）进来做 prefill，会占用大量算力。此时正在进行的 decode 请求被挤到后面——**TPOT 出现尖刺**。

用户体验上，这就是「聊着聊着突然卡一下，然后又快了」。在 TPOT 的 P99 曲线上，这是一根刺。

### 13.1.3 伤害二：Decode 占着显存，限制 Prefill

反过来，为了支撑高并发，decode 需要大量 KV Cache 显存。这部分显存被长期占用，prefill 阶段能用的显存就少了——影响 prefill 的分块大小和可承载的输入长度。

### 13.1.4 伤害三：配比无法独立调整

最根本的问题是这个。

一个典型的在线服务，输入 2K token、输出 500 token。粗略估算：

- Prefill 阶段：一次性处理 2000 token，算力密集
- Decode 阶段：500 步，每步带宽密集

这两个阶段对 GPU 数量的需求比大概是某个固定值。但**这个比值会随业务变化**——如果明天上了长文档问答，prefill 需求翻倍；如果改成短聊天，decode 需求上升。

**混部架构下，你只能按最坏情况配置整机，然后忍受大量资源错配。**

### 13.1.5 收益到底有多大

PD 分离的收益来源有三个：

| 收益来源 | 说明 |
|---|---|
| **消除干扰** | decode 的 TPOT 不再被 prefill 打断，P99 显著改善 |
| **独立配比** | prefill 池和 decode 池按实际负载各自扩缩容 |
| **独立优化** | prefill 节点可以用大 batch、高算力配置；decode 节点可以选高带宽、大显存配置 |

但收益有多大完全取决于负载。**短输入、长输出的场景，prefill 占比很小，分离收益有限；长输入、短输出的 RAG 场景，收益最明显。**

## 13.2 PD 分离架构解剖

![PD 分离：prefill 池与 decode 池各配各的卡，中间用高速网络传 KV](./assets/ch13-pd-disaggregation.png)

### 13.2.1 整体结构

```
                    ┌──────────────┐
    请求 ──────────▶│   调度器      │  决定请求路由到哪个 prefill / decode 节点
                    └──────┬───────┘
                           │
              ┌────────────┴────────────┐
              ▼                         ▼
    ┌──────────────────┐      ┌──────────────────┐
    │  Prefill 池       │      │  Decode 池        │
    │  算力密集配置      │      │  带宽/显存密集配置  │
    │  处理 prompt      │      │  逐 token 生成     │
    │  产出 KV Cache    │      │                   │
    └────────┬─────────┘      └────────▲──────────┘
             │                         │
             │   KV Cache 传输          │
             └─────────────────────────┘
              （NVLink / RDMA / GPUDirect）
```

### 13.2.2 请求的一生

1. 请求到达调度器
2. 调度器选一个 **Prefill 节点**，把 prompt 发过去
3. Prefill 节点计算并产出 prompt 的 KV Cache（**同时生成第一个 token**）
4. KV Cache 通过高速网络传给某个 **Decode 节点**
5. Decode 节点接管，逐步生成剩余 token
6. 生成结束，释放 KV Cache

**关键在第 4 步。** 这一步的耗时，直接决定了 PD 分离是赚是亏。

### 13.2.3 KV 传输层

| 技术 | 作用 | 适用场景 |
|---|---|---|
| **NIXL** | NVIDIA 的点对点 KV 传输库，统一抽象 NVLink / RDMA / GPUDirect | 当前主流方案 |
| **GPUDirect RDMA** | GPU 显存直接跨节点传输，绕过 CPU 内存中转 | 跨节点必备 |
| **NVLink** | 机内多卡高速互联 | 单机内分离 |
| **RDMA / RoCE / InfiniBand** | 跨节点高带宽低延迟网络 | 跨节点分离 |

### 13.2.4 分布式 KV 存储

比点对点传输更进一步的是**把 KV 做成集群级共享资源**。

Mooncake 是这一思路的代表：KV 块通过 RDMA 在集群内共享，任何节点都能读取。据公开报告，在 agentic 这类大量请求共享长上下文历史的负载上，命中率可达 90% 以上，带来数倍的吞吐提升与数量级的 TTFT 下降（数据来源：公开技术报告，具体数值随配置差异大，请以实测为准）。

**思路上要注意**：分布式 KV 存储不是 PD 分离的必要组件，但它是前缀缓存在 PD 分离架构下的自然延伸——分离之后仍然要保持跨请求的 KV 复用，否则就浪费了第 4 章讲的那些红利。

### 13.2.5 分离之后，前缀缓存怎么办

这是个容易被忽略的工程难点。

Prefill 和 Decode 分到不同节点后，RadixAttention / prefix cache 的树结构就不再局限于单机。需要解决：

- Prefill 节点命中缓存后，是否还需要传输 KV？（如果 decode 节点已有，可以跳过）
- 缓存元数据如何在集群内同步？
- 淘汰策略如何在分布式环境下保持一致？

**这也是为什么 PD 分离的成熟度高度依赖引擎版本**——早先的实现会直接放弃跨节点前缀缓存，后来的版本才逐步补上。落地前务必确认你用的版本在这方面的行为。

## 13.3 vLLM 的 PD 分离

### 13.3.1 核心机制：KV Connector

vLLM 通过 **KV Connector** 抽象层实现 PD 分离。核心思路是把 KV Cache 的生产者和消费者解耦：

- **Producer（生产者）**：Prefill 实例，产出 KV Cache
- **Consumer（消费者）**：Decode 实例，消费 KV Cache
- **Connector**：负责实际的传输，可插拔（NIXL、Mooncake 等）

### 13.3.2 启动方式

> ⚠️ **版本提示**：PD 分离相关的参数名在 vLLM 近几个版本变动较快。以下为典型形态，**务必以你所用版本的官方文档为准**。

**Prefill 实例（生产者）**

```bash
# 适用于 vLLM v0.20.x 典型形态，参数名请以官方文档为准
vllm serve Qwen/Qwen3-8B \
    --tensor-parallel-size 2 \
    --port 8100 \
    --kv-transfer-config '{
        "kv_connector": "NixlConnector",
        "kv_role": "kv_producer",
        "kv_buffer_size": "8GB"
    }'
```

**Decode 实例（消费者）**

```bash
vllm serve Qwen/Qwen3-8B \
    --tensor-parallel-size 2 \
    --port 8200 \
    --kv-transfer-config '{
        "kv_connector": "NixlConnector",
        "kv_role": "kv_consumer",
        "kv_buffer_size": "8GB"
    }'
```

**配套的路由层**：PD 分离需要一个知道「哪些是 prefill 节点、哪些是 decode 节点」的代理层来编排请求的两段式流转。vLLM 生态里有相应的 router 组件，具体方案请查阅对应版本的官方文档。

### 13.3.3 三个已知的工程坑

**坑一：多副本部署时的配对问题**

当你部署多个 prefill 副本和多个 decode 副本时，prefill 节点必须知道该把 KV 发给谁。如果路由层没有做正确的配对和状态跟踪，会出现 KV 发错节点、请求挂起等问题。

**这是社区里反馈最多的问题**——它不是性能问题，而是正确性问题，排查起来很痛苦。

**坑二：buffer size 设置**

`kv_buffer_size` 太小会导致传输阻塞、请求排队；太大则浪费显存。这个参数需要根据「并发数 × 单请求 KV 大小」来估算，参考 13.5 节的计算方法。

**坑三：显存预算要重新算**

PD 分离后，prefill 节点和 decode 节点的显存需求不同：

- Prefill 节点：需要足够显存放**瞬时**的 KV（处理完就传走），buffer 够大即可
- Decode 节点：需要长期持有**所有在途请求**的 KV，显存压力更大

**不要用同一份显存配置去套两类节点。**

## 13.4 SGLang 的 PD 分离

### 13.4.1 启动方式

SGLang 的 PD 分离通过 `--disaggregation-mode` 指定节点角色：

> ⚠️ **版本提示**：以下为典型形态，参数名与可用选项以 SGLang 官方文档为准（基于 v0.5.18+）。

**Prefill 节点**

```bash
python -m sglang.launch_server \
    --model-path Qwen/Qwen3-8B \
    --disaggregation-mode prefill \
    --disaggregation-transfer-backend nixl \
    --port 30000
```

**Decode 节点**

```bash
python -m sglang.launch_server \
    --model-path Qwen/Qwen3-8B \
    --disaggregation-mode decode \
    --disaggregation-transfer-backend nixl \
    --port 30001
```

**路由层**：SGLang Router 支持 PD 分离模式下的请求编排，也可用 NVIDIA Dynamo 等外部编排层。

### 13.4.2 与 vLLM 的实现差异

| 维度 | vLLM | SGLang |
|---|---|---|
| 抽象方式 | KV Connector（producer/consumer） | `--disaggregation-mode` 角色指定 |
| 传输后端 | NIXL、Mooncake 等可插拔 | NIXL、以及 Dynamo 集成 |
| 前缀缓存协同 | 逐步补齐中，版本依赖强 | RadixAttention 原生设计上更贴近分离架构 |
| 路由层 | 社区方案 + 外部编排 | SGLang Router 原生支持 |

**不要过度解读这张表。** 两个引擎的 PD 分离都在快速迭代，能力边界每个版本都在变。**选型前请查当前版本的官方文档和 release notes。**

### 13.4.3 验证是否真的分离了

部署完别急着信，验证三件事：

1. **看日志**：确认 prefill 节点和 decode 节点的启动日志中角色标识正确
2. **看指标**：prefill 节点应该几乎没有 decode 活动，decode 节点不应该有大规模 prefill
3. **压测对比**：同一负载下，对比分离前后的 TTFT 与 TPOT 分布（重点看 P99）

## 13.5 网络要求与成本账 ⏭️

![KV 传输：分离之后 KV Cache 要跨机器搬，网络随即成为新的瓶颈](./assets/ch13-kv-transfer.png)

> 这一节回答一个最关键的问题：**你的网络撑不撑得起 PD 分离？** 算不清这笔账，分离可能让你变慢。

### 13.5.1 先算要传多少数据

KV Cache 的大小用第 4.1 节的公式：

```
KV_bytes = 2 × layers × kv_heads × head_dim × seq_len × dtype_bytes
```

**算个具体的**（Llama-3.1-8B：32 层、8 个 KV head、head_dim 128、BF16）：

| 输入长度 | 单请求 KV 大小 |
|---|---|
| 2,048 token | ≈ 268 MB |
| 4,096 token | ≈ 536 MB |
| 8,192 token | ≈ 1.07 GB |
| 32,768 token | ≈ 4.3 GB |

**注意这个量级**——一个 32K 长上下文请求，要传 4.3 GB 数据。

### 13.5.2 再算需要多少带宽

设你能接受的 KV 传输耗时上限为 `T`（这个时间会**直接加到用户的 TTFT 上**），则所需带宽：

```
所需带宽 = KV 大小 ÷ T
```

举例：8K 输入（1.07 GB），要求传输在 100ms 内完成：

```
所需带宽 = 1.07 GB ÷ 0.1 s ≈ 10.7 GB/s ≈ 86 Gbps
```

再举：32K 输入（4.3 GB），同样要求 100ms：

```
所需带宽 ≈ 43 GB/s ≈ 344 Gbps
```

### 13.5.3 对照常见网络的实际能力

| 网络 | 典型带宽 | 传 1.07 GB（8K 输入）耗时 |
|---|---|---|
| 万兆以太网（10 GbE） | ≈ 1.25 GB/s | ≈ 860 ms |
| 25 GbE | ≈ 3.1 GB/s | ≈ 345 ms |
| 100 GbE / RoCE | ≈ 12.5 GB/s | ≈ 86 ms |
| InfiniBand HDR（200 Gbps） | ≈ 25 GB/s | ≈ 43 ms |
| NVLink（机内） | 数百 GB/s 量级 | 数 ms |

（数值为理论峰值，实际有效带宽通常为峰值的 60%–80%，请以实测为准）

**结论非常直接**：

- **万兆网环境下做 PD 分离，几乎必然是亏的**——单是传输就要 860ms，比 prefill 本身还慢
- **100 GbE 是起步线**，且只在中短输入场景成立
- **长上下文场景（32K+）需要 200 Gbps 以上，或者干脆 reconsider**

### 13.5.4 盈亏平衡的判断式

PD 分离是否划算，可以简化为比较两件事：

```
收益 = 消除干扰带来的延迟改善 + 独立配比带来的资源利用率提升
成本 = KV 传输耗时（直接加到 TTFT）+ 调度复杂度 + 运维成本
```

一个粗略但实用的判据：

> **如果 KV 传输耗时 > 该请求 prefill 耗时的 30%，分离大概率是亏的。**

因为此时传输本身就抵消掉了分离带来的大部分收益。

### 13.5.5 降低成本的几个手段

如果网络是瓶颈，但业务确实需要分离：

| 手段 | 效果 | 代价 |
|---|---|---|
| **KV 量化传输** | 传输量减半（FP16 → FP8） | 轻微的精度损失 |
| **只传必要部分** | 命中前缀缓存时不重复传 | 依赖缓存协同实现 |
| **同机内分离** | 走 NVLink，带宽高一个量级 | 失去跨节点弹性 |
| **分层传输** | 关键层优先传，重叠计算与传输 | 实现复杂度高 |

## 13.6 什么时候不该做 PD 分离

这一节可能比前面所有内容都重要。

### 13.6.1 五个门槛

| 门槛 | 具体判据 |
|---|---|
| **规模门槛** | GPU 总数少于 8–16 卡时，分离带来的配比收益通常抵不过复杂度和传输成本 |
| **网络门槛** | 没有 RDMA / RoCE（100 Gbps 起）时，不要做跨节点分离 |
| **负载门槛** | 输入短、输出长的场景（如纯生成、闲聊），prefill 占比小，收益有限 |
| **团队门槛** | 没有能力排查分布式问题（KV 传错、节点失联、buffer 溢出）时 |
| **稳定性门槛** | 业务还在快速迭代、负载特征每周都变时，配比优势无法稳定发挥 |

### 13.6.2 决策清单

逐条自检，**任何一条答「否」都建议先不要上 PD 分离**：

- [ ] GPU 规模是否 ≥ 8 卡，且 prefill 与 decode 的资源需求比明显偏离 1:1？
- [ ] 是否有 100 Gbps 以上的 RDMA 网络（跨节点场景）？
- [ ] 实测中，TPOT 的 P99 是否明显差于 P50（说明存在 prefill 干扰）？
- [ ] 负载是否以长输入为主（输入长度 ≥ 输出长度的 2 倍）？
- [ ] 估算的 KV 传输耗时是否低于 prefill 耗时的 30%？
- [ ] 团队是否有排查分布式传输问题的能力和时间？
- [ ] 是否已经把单机优化做到位（第 10 章的参数调优都试过了）？

**最后一条尤其重要。** PD 分离是第三阶段四（0.7.4 节）的优化，如果前面的优化还没做（前缀缓存没开、投机解码没试、参数还是默认值），先做那些——**投入产出比高得多，风险低得多。**

### 13.6.3 一个反直觉的提醒

> **PD 分离把「显存不够」的问题，换成了「网络不够快」的问题。**

它不是银弹，是一次**问题转移**。在决定之前，先确认新位置的痛比旧位置轻。

## 13.7 没有集群怎么学习这一章

这章标了 ☁️，但并不意味着没集群就完全学不了。

### 13.7.1 单机模拟

如果你有一台多卡机器（哪怕只有 2 张卡），可以完整模拟 PD 分离：

```bash
# 卡 0 做 prefill，卡 1 做 decode（以 SGLang 形态示意，参数以官方文档为准）
CUDA_VISIBLE_DEVICES=0 python -m sglang.launch_server \
    --model-path Qwen/Qwen3-8B --disaggregation-mode prefill --port 30000

CUDA_VISIBLE_DEVICES=1 python -m sglang.launch_server \
    --model-path Qwen/Qwen3-8B --disaggregation-mode decode  --port 30001
```

单卡机器也可以——用更小的模型，prefill 和 decode 各占一部分显存跑在同一张卡上。此时走的是本机内存拷贝而非 RDMA，**性能数据没有参考价值，但架构行为是真的**，足以搞懂请求如何流转、KV 如何传递。

### 13.7.2 用计算代替实测

13.5 节那套计算，不需要任何硬件就能做：

1. 查你的目标模型的 config.json，拿到 layers / kv_heads / head_dim
2. 用公式算出你的典型输入长度对应的 KV 大小
3. 查你的网络带宽，算出传输耗时
4. 和该请求的 prefill 耗时对比

**这套推演能告诉你 80% 的结论**——至少能判断出「该不该往下投入」。

### 13.7.3 看架构和实现

如果连实验环境都没有，退一步：

- 读 vLLM 的 KV Connector 抽象层代码，理解 producer / consumer 的接口设计
- 读 SGLang 的 disaggregation 实现，理解请求流转的状态机
- 关注两个引擎的 release notes，看 PD 分离相关的能力演进

理解设计比跑通命令更有长期价值——毕竟等你有集群的时候，命令可能已经变了。

## 本章小结

1. **PD 分离的动因是三个伤害**：prefill 打断 decode 造成 TPOT 尖刺、decode 占显存限制 prefill、两阶段资源配比无法独立调整。

2. **架构三要素**：Prefill 池（算力密集配置）、Decode 池（带宽显存密集配置）、KV 传输通道（NIXL / RDMA / GPUDirect）。分布式 KV 存储是前缀缓存在分离架构下的自然延伸，不是必需组件。

3. **vLLM 用 KV Connector 抽象（producer / consumer）**，SGLang 用 `--disaggregation-mode` 指定角色。两者都在快速迭代，参数名务必以当前版本官方文档为准。

4. **网络成本账是决策核心**：8K 输入的 KV 约 1 GB，100 Gbps 网络传约 86ms。**万兆网环境下做跨节点分离几乎必然亏本。** 粗略判据：传输耗时超过 prefill 耗时的 30%，分离大概率不划算。

5. **五个不该做的门槛**：规模不足 8–16 卡、无 100 Gbps RDMA、负载以短输入长输出为主、团队无分布式排障能力、负载特征不稳定。

6. **最重要的提醒**：先把单机优化做透（第 10 章），再考虑 PD 分离。它是第三代里最靠后的一个阶段，投入产出比低于前面的阶段。

7. **没集群也能学**：单机多卡（甚至单卡小模型）可完整模拟架构行为；13.5 节的计算不需要任何硬件就能给出 80% 的结论。
