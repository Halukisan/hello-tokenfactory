# 第 9 章　vLLM 核心能力

第 8 章让你「跑起来」了。这一章回答「除了跑起来还能干什么」——量化瘦身、结构化输出、多 LoRA、多模态、非生成模型，以及 RL 的 Sleep Mode。每节先给「值得用 / 不值得用」，再讲做法和坑。

## 9.1 多卡与多机部署

单卡能放下权重（BF16 下「模型参数 × 2 字节 < 0.9 × 单卡显存」）就别上并行——并行有通信成本。

模型放不进单卡，第一反应应该是 **TP（张量并行）**，且尽量在**单机 NVLink 域内**完成。

```bash
# 单机 4 卡跑一个 32B 级模型（若用 8×80GB 机器，70B 也可 TP8 单节点）
vllm serve Qwen/Qwen3-32B \
    --tensor-parallel-size 4 \      # 把一层权重切到 4 张卡
    --gpu-memory-utilization 0.90
```

TP 把每层矩阵乘法按列/行切分再 all-reduce 合并，所以**卡间高带宽是前提**：NVLink 微秒级、跨节点 IB 毫秒级，差两个数量级；通信量还与「层数 × 隐藏维 × 序列长」正相关。

> **反模式：TP 跨节点**。把 `--tensor-parallel-size 8` 铺到两台 4 卡机器上，每层 all-reduce 都得过网络，通信开销会吃掉切分收益，结果可能比单节点 TP4 + PP2 还慢。vLLM 不会阻止你这么干，但物理会。

单机 8 卡 TP 仍装不下时引入 **PP（流水并行）**：前若干层放机器 A、后若干层放机器 B，请求像流水线穿过。

```bash
# 单机 8 卡都切满时，TP8 + PP2 把 16 卡用上（示意）
vllm serve <70B级模型> \
    --tensor-parallel-size 8 \
    --pipeline-parallel-size 2 \
    --gpu-memory-utilization 0.90
```

PP 的问题是 **bubble（流水线气泡）**：段间有等待空窗，切得越碎占比越高；实践中 TP 优先用满单机，PP 只作补充。

> 并行策略的「甜点」顺序永远是：单卡能跑 → 单机 TP → 单机 TP+PP → 多机 DP/PP。每升一档，运维复杂度和通信成本都上一个台阶。我见过有人一上来就 TP2+PP4 跨两机，结果 bubble 加网络延迟让吞吐比单机 TP8 还低。**并行是被迫的选项，不是越多越好。**

多机两种切法：**PP 跨机**（段间传整段激活值，量小但仍同步）；**DP**（每机一份完整权重和 KV 池，吞吐线性扩展）。启动配好 NCCL，用 `--nnodes 2 --node-rank 0/1 --distributed-executor-backend ray` 编排，核心要求是**节点间高速互联（InfiniBand / 200G+ 以太网 + GPUDirect）**。

> 多机部署真正的工程难点不是命令，而是**网络与 NCCL**。最常见的卡死现象是「进程起得来、但一直不动」，十有八九是 IB 接口没选对、或 `NCCL_SOCKET_IFNAME` 指错了网卡。上线前用 `NCCL_DEBUG=INFO` 跑一次，确认 all-reduce 走的是你期望的高速接口，别等压测时才暴露。另外多机 DP 务必配合缓存感知路由（第 2.6 / 12.4 节），否则前缀缓存命中率被稀释为 1/N。

**值得用**：70B+ 单节点 TP 装不下，或需 DP 扩吞吐且请求量够大。**不值得用**：中小模型硬上多机——复杂度、网络成本和故障面都上来了。

## 9.2 量化实战

![量化：把大模型压成更小的一份，省下的显存直接变成可用的并发](./assets/ch09-quantization.png)

量化用「精度」换「显存 / 带宽 / 吞吐」，ROI 最高也最容易翻车，代价必须自己测。

| 方案 | 量化对象 | 典型压缩 | 适用场景 |
|---|---|---|---|
| **FP8**（E4M3 / E5M2） | 权重 + 激活（计算） | ~2× 显存 | H 系列及以后，几乎无损首选，在线量化 |
| **INT8（W8A8）** | 权重 + 激活 | ~2× | 无 FP8 单元的卡（如 A100），动态量化 |
| **AWQ**（W4A16） | 权重 4bit | ~4× 显存 | 需校准；显存吃紧、保效果优先 |
| **GPTQ**（W4A16） | 权重 4bit | ~4× | 需校准；同 AWQ，社区模型多 |
| **INT4（纯权重量化）** | 权重 4bit | ~4× | 需校准；极致省显存，效果代价最大 |
| **NVFP4 / MXFP4** | 权重 + 激活 | 更高 | 硬件原生，Blackwell（B200 等）新卡专用 |

> **关键区分**：上面这些方案分三类，很多人混为一谈——

- **权重量化**（AWQ / GPTQ / INT4）：只压权重，激活仍高精度，省**显存**，对 decode 带宽墙帮助有限。
- **动态量化 / 激活量化**（FP8 / INT8 W8A8）：权重和激活都压，既省显存又减访存量，直接缓解内存墙。
- **KV Cache 量化**（FP8 KV，见 5.4.1）：压 KV 缓存，针对长上下文显存膨胀。

三类可**叠加**（如「AWQ 4bit + KV FP8」），但每叠一层都是一次精度妥协，叠加后必须重做 9.2 节的评估。

**值得用**：显存放不下、带宽墙明显、长上下文。**不值得用**：效果敏感任务压到 4bit 又不做校准验证；硬件原生支持 FP8 却用 INT4。

权重量化要先用校准集「感知」哪些权重重要。vLLM 直接加载社区已量化的权重（如 Qwen3.5-0.8B 的社区 AWQ）最省事；自己量化：

```bash
# AWQ：需要一份校准集（小样本代表分布），产出量化权重目录，工具 autoawq
python -m awq.entry --model_path Qwen/Qwen3.5-0.8B \
    --w_bit 4 --q_group_size 128 \
    --output_dir ./models/Qwen3.5-0.8B-AWQ

# GPTQ 类似（auto-gptq / mlc-llm）；产出后 vLLM 用 --quantization awq / gptq 加载
vllm serve ./models/Qwen3.5-0.8B-AWQ --quantization awq
```

> 校准集的质量直接决定 4bit 效果。用和你业务同分布的几百条样本做校准，比用通用 Wiki 文本好得多——这是「通用量化权重在你业务上掉点」的常见根因。如果手上没有现成量化权重，宁可先用 FP8 在线量化（几乎无损），也不要随便拉一个分布不匹配的 4bit 权重上线。

不想离线量化，可在启动时让引擎**边加载边量化**（TurboQuant 思路，vLLM v0.20+），代价是启动多一次转换、格式受版本限制：

```bash
# 在线 FP8 量化：权重以 FP8 加载，免去预量化流程
vllm serve Qwen/Qwen3-32B \
    --quantization fp8        # 在线把权重转 FP8，无需事先准备量化权重
```

> 在线量化适合「先跑起来看效果」的验证阶段。一旦确定用某个格式生产，我更建议**预量化一份落盘**，好处是启动快、行为可复现、能离线校验精度。在线量化把「转换」和「服务」绑在一起，出问题难定位到底是量化坏了还是服务坏了。

精度评估分两层：**perplexity** 看语言建模能力（升高 1% 内无感，5%+ 警惕）；**业务指标**才定生死（分类准确率、抽取 F1、编译通过率）。用 `src/ch09-vllm-features/quantization_compare.py` 在同一硬件、同一数据集上把吞吐与指标成对测出（见 9.2 节的评估方法），找**拐点**：指标不显著下降的区间里选吞吐最高。

> **这是全节最重要的提醒：不能只看吞吐。** 量化带来吞吐提升的同时，必然伴随精度变化。很多团队上线 FP8 后「吞吐翻倍、线上客诉翻倍」——因为只盯了吞吐指标。

> **反模式**：只看「官方说 FP8 吞吐翻倍」就全量上线。官方数字是他们硬件、他们模型上的结果。你的模型、你的数据、你的卡，结论未必一致。量化是唯一一个「收益和代价都高度依赖你的具体负载」的优化手段，必须本地实测。

> 我见过最稳的量化决策流程是「先 AWQ/GPTQ 4bit 保效果下限，再叠 FP8 看能否再挤」，而不是直接跳到最低 bit。量化不是越狠越好，是「在效果红线内尽量省」。第 8 章提到的 `kv-cache-dtype` 量化要单独评——它影响的是长上下文下的生成质量，短文本测不出来。另外 NVFP4 / MXFP4 是 Blackwell 等新硬件专属，老卡设了也不会生效，别在 A100 上白费功夫。

> **反模式收尾**：有人看到「INT4 显存只有 1/4」就直接上，结果业务指标掉了 8%，线上客诉爆发。省下的显存如果是为了「能跑」，那值得；如果只是为了「更便宜」却牺牲效果，多数业务场景划不来。**量化是手段不是目标，效果红线才是约束。**

## 9.3 结构化输出

只要下游是程序（Agent 工具调用、数据抽取、表单填充），结构化输出就是**必选项**——「生成后正则解析」在生产上不可接受。

原理是把 JSON Schema / 正则 / EBNF 约束编译成有限状态机（FSM），每步把非法 token 的 logits 置为 `-inf`，**非法输出在物理上不可能产生**。

```python
# ch07-vllm-features/structured_output.py  （vLLM v0.20+，OpenAI 兼容接口）
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")

# JSON Schema（最常用）；正则用 guided_regex，语法用 guided_grammar
schema = {
    "type": "object",
    "properties": {
        "city": {"type": "string"},
        "temperature": {"type": "number"},
        "unit": {"enum": ["C", "F"]},
    },
    "required": ["city", "temperature", "unit"],
}
resp = client.chat.completions.create(
    model="Qwen/Qwen3.5-0.8B",
    messages=[{"role": "user", "content": "北京现在多少度？用结构化返回。"}],
    max_tokens=256,
    extra_body={"guided_json": schema},   # vLLM 的 JSON 约束入口
)
```

后端有 **xgrammar** 与 **guidance** 两类：xgrammar 走压缩 FSM + jump-forward，把必然连续的 token 串一次吐出，开销更低；guidance 更灵活、生态更老。默认通常走 xgrammar，不支持的复杂约束再退 guidance。

> JSON Schema 里尽量给 `enum` 和 `type` 收窄范围，约束越紧，FSM 越早收敛，生成越快、越不容易跑偏。反过来，一个「`properties` 几乎无限制」的 JSON 约束，等于没怎么约束，收益很小却仍要付出 FSM 开销。**结构化输出不是「开了就免费」，约束的构造本身是一门手艺。**

边界：复杂 schema 部分后端不支持或降级，上线前用真实 schema 实测；流式下完整 JSON 要等结束才能解析。

与投机解码（第 7 章）同开会**抢「下一步 token」的决策权**：draft 猜 token、FSM 屏蔽非法 token，需保证约束优先；vLLM 支持协同，但**实测接受率会因约束下降**。

> 结构化输出 + 投机解码一起开时，务必单独测一遍端到端延迟。理论上两者可叠加收益，但约束越紧（如很窄的正则），投机的解码步越短，draft 优势越弱。窄约束场景下，投机解码的收益可能微乎其微，反而增加复杂度。**值得用**：宽 JSON / 长生成配投机；**不值得用**：极窄正则还硬上投机，纯属增加排查成本。

工具调用是结构化输出的特例：

> **实测建议**：用一组真实的工具 schema（带嵌套对象、枚举、必填字段）跑 100 次，统计「一次成型、无需重试」的比例。这个比率比「能生成 JSON」重要得多——生产上每多一次重试就是一次额外往返延迟。具体比率以你自己的 schema 复杂度和模型实测为准。一个常见的失败模式是：模型把参数填对了，但「函数名」拼错或多了额外字段，调用方解析失败——这类要在 system prompt 和 schema 上同时约束。

约束也不免费：FSM 状态在 CPU 侧维护并与 GPU 解码同步，同等并发下吞吐略降，降幅与约束复杂度正相关（宽 JSON 几个百分点，极复杂 EBNF 可能两位数）。超出 SLO 预算时：收紧 schema、降并发，或拆实例。

## 9.4 多 LoRA 服务

![一个基座模型挂多个 LoRA 适配器，共享同一份显存](./assets/ch09-multimodal-lora.png)

当「一个底座 + 多个垂直适配器」是真实架构（多租户、多任务、个性化），多 LoRA 是**降本利器**；若各任务模型本就不同，强行合并是给自己找麻烦。

| 维度 | 多 LoRA（单底座） | 多独立实例 |
|---|---|---|
| 权重显存 | 1 份底座 + N 份 LoRA（小） | N 份完整权重 |
| 切换成本 | 热加载 / 卸载，毫秒级 | 起停实例，分钟级 |
| 隔离性 | 弱（同进程） | 强 |
| 适用 | 同底座多任务 | 完全不同的模型 |

适配器通常只有底座的 0.1%–5%（取决于 rank）：「一份底座 + 10 个 LoRA」远小于「10 个独立实例」——8B 底座约 16GB，rank=64 的 LoRA 几十 MB，10 个几百 MB，10 个独立实例却要 160GB。

> **前提提醒**：所有 LoRA 必须共享**同一个底座模型**。vLLM 一个实例挂一个底座，不同底座的 LoRA 得起不同实例。如果你的任务是「完全不同的模型」，多 LoRA 帮不上忙，那是多实例或模型路由的事。

```bash
# 启动时挂载多个 LoRA（vLLM v0.20+）
vllm serve Qwen/Qwen3.5-0.8B \
    --enable-lora \
    --lora-modules sql=/path/lora-sql math=/path/lora-math code=/path/lora-code \
    --max-lora-rank 64 \          # LoRA 秩上限，影响显存
    --max-lora-num 4                # 同时驻留的 LoRA 数上限
```

调用时用 `extra_body={"lora_request": {"name": "sql"}}` 指定适配器。**并发 LoRA 数限制**是关键：`--max-lora-num` 限制同时驻留的适配器数，超过后排队或换入换出；`max-loras-per-batch` 限制单批内可混合的 LoRA 种数，太多会拖慢 batch 整理。

> 多 LoRA 最常见的线上问题是「热点不均 + 长尾」。少数 LoRA 被高频调用（该常驻），大量 LoRA 偶尔来一次（不该占显存）。盲目把 `max-lora-num` 开很大，显存被长尾适配器占满，热点反而被挤。建议：高频适配器常驻（在启动 `--lora-modules` 里挂上），长尾走按需加载，并用监控看「LoRA 换入换出次数」——它高说明你的 `max-lora-num` 配小了或负载画像错了。

ROI 还要算**隔离性代价**（一个适配器 OOM 波及同实例）、**热点换入开销**和运维复杂度。

**值得用**：N ≥ 3、共享同一底座、多租户 / 多任务 / 个性化、切换频繁。**不值得用**：任务间模型本就不同，或隔离性要求强（金融、医疗合规）——该用独立实例。

## 9.5 多模态部署

视觉语言模型（VLM，如 Qwen-VL 系列）的部署难点不在「能不能跑」，而在**预处理与 GPU 解耦**——把图像 resize / 编码放到 CPU 或独立进程，GPU 只管核心推理，否则预处理会拖垮整卡吞吐。

```bash
# VLM 起服务与文本模型命令基本一致（vLLM v0.20+ 原生支持主流 VLM）
vllm serve Qwen/Qwen3.5-0.8B \
    --limit-mm-per-prompt image=4    # 限制每条请求最多 4 张图，控显存
```

图像输入要经解码 → resize → 归一化 → 视觉塔编码（ViT），其中**解码和 resize 是 CPU 密集、且与 GPU 推理无数据依赖**，混在推理进程里会让 GPU 空转。正确做法是把上传、转码、缓存**前置到网关或独立 worker**，让预处理与推理分别扩缩。

一张图的视觉 token 数取决于分辨率和分块策略，**直接进 KV Cache 账本**——「一张图」等价于「几千个文本 token」：

```
单请求显存占用 ∝ (文本token + 图像视觉token) × 每层KV大小
并发上限 ≈ KV池 / 单请求占用
```

所以先分清「图太多」还是「请求太多」：前者降 `--limit-mm-per-prompt`，后者降 `max-num-seqs`；很多团队按后者砍并发，根因其实是单图 token 爆炸。实测读 `usage.prompt_tokens`（已含视觉 token），回 5.4.2 的公式配容量。

> VLM 的「图像 token 数」对成本影响极大，但默认配置往往很宽松（高分辨率、多切片）。上线前用一张典型图实测它的视觉 token 数（引擎日志或 profiling 能看到），再据此配 `--limit-mm-per-prompt` 和并发。盲目高分辨率 = 隐性地把每张图变成几千 token，KV 池瞬间被吃光。

## 9.6 Embedding / Rerank / Reward Model

RAG 里这三样是「非生成」刚需，但和生成模型是**不同的服务形态**——不要用一个生成 endpoint 硬凑，要各自独立部署。

| 模型类型 | 输出 | 典型用途 | vLLM 部署方式 |
|---|---|---|---|
| **Embedding** | 向量（定长） | 向量库检索、语义召回 | `vllm serve <emb模型>`，走 `/v1/embeddings` |
| **Rerank** | 相关性分数 | 召回后精排 | `vllm serve <rerank模型>`，走 `/v1/rerank` |
| **Reward Model** | 标量奖励 | RLHF 对齐、自我评判 | `vllm serve <reward模型>`，走 `/v1/score`（或 reward 专用接口） |

三类都不是自回归生成——一次前向出结果，没有逐 token 解码，所以**吞吐远高于生成模型**。把它们和生成模型混在一个实例里会互相抢 KV 池和调度，是明显的反模式。标准链路是 Embedding 召回 Top-K → Rerank 精排 → 生成；三者独立部署，Embedding / Rerank 是单步前向，副本可多于生成实例。

> RAG 链路里最常被忽视的是 Rerank 的引入时机。很多团队只用 Embedding 召回就直接喂生成，结果召回的 Top-K 里相关文档排在第 8 位，生成模型「看到了但没优先用」。加一层 Rerank 往往比「加大生成模型」带来的回答质量提升更明显，且成本低得多。Reward Model 在 RLHF / 自我批判（如让模型给自己的回答打分）里用，是 RL 训练循环的高频调用方（见 9.7.2 节）。

**值得用**：RAG / 检索 / 对齐训练场景，独立部署各司其职。**不值得用**：为了「少起一个服务」把 Embedding 和生成塞一起——后期扩容时你会后悔。

## 9.7 特殊场景能力 ⏭️

### 9.7.1 Sleep Mode：显存让渡

RL 训练循环里，同一台机器既要跑训练又要跑推理 rollout，无法同时占满显存。**Sleep Mode** 让推理引擎在「不服务时」把显存让渡给训练进程，需要时再「唤醒」重新分配（vLLM 通过权重卸载 / 重新映射实现，命令以版本为准）。唤醒有开销，所以它是「时间错峰复用」而非「随时切换」。

**值得用**：RL 训练机与推理机复用同一批 GPU、资源时间错峰。**不值得用**：纯推理服务——唤醒有开销，无谓地开反而拖慢首请求。

### 9.7.2 RL 集成与训练-推理一致性

RLHF / RLVR 把推理引擎变成 rollout 执行体：训练循环产出新权重 → 推给引擎生成样本 → 算 reward → 更新。这里有个致命的要求：**训练框架和推理引擎对同一权重的数值结果必须一致**，否则 reward 信号被引擎差异污染。

> 训练-推理一致性问题往往以「reward 曲线不收敛但单测都对」的诡异形式出现。排这类问题时，先固定一个 batch 在两边各跑一次前向，逐层 diff 输出——差异通常出在 attention backend 或 dtype 边界。一个实用 checklist：① 两边用同一 attention 实现（如都走 FlashAttention 同版本）；② dtype 一致（BF16 vs FP16 别混）；③ 归一化（RMSNorm）的 eps 与计算顺序一致；④ RoPE 位置编码实现对齐。vLLM 的 V1 引擎和主流训练框架的对齐在持续改进，但跨版本仍要自己验证一次。

## 本章小结

1. **并行首选单机 TP**：放不下才上并行，TP 尽量在 NVLink 域内；跨节点 TP 是反模式，收益被网络吞掉。
2. **量化分三类、必须双指标评估**：权重量化省显存、动态量化压带宽墙、KV 量化压长上下文；perplexity 粗筛 + 业务指标定生死，只看吞吐上线必然翻车。
3. **结构化输出是必选项**：FSM 约束让非法输出物理上不可能产生；与投机解码叠加时要重测接受率和延迟。
4. **多 LoRA 适合同底座多任务**：一份权重服务多适配器，省显存；但要按「热点常驻、长尾按需」管理并发数。
5. **非生成模型要拆开部署**：Embedding / Rerank / Reward 吞吐特征不同，混在生成实例里会互相抢资源。
