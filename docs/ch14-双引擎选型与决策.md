# 第 14 章　双引擎选型与决策

> **本章要回答的问题**
> 1. vLLM 和 SGLang，我的场景到底该用哪个？
> 2. 其他引擎（TensorRT-LLM / LMDeploy / TGI / Ollama）各自的位置在哪里？
> 3. 国产硬件上跑推理，现状如何、迁移成本多大？
> 4. 有没有一张可执行的决策流程图，从「模型 + 硬件 + 负载 + 团队」四要素走到结论？

难度 ★★☆　|　硬件要求：无（纯决策章节）　|　⏭️ 14.3 节（国产硬件）按需选读

> **本章的立场**：引擎选型没有放之四海皆准的答案。本章不做「谁更快」的空洞结论——性能对比的结论保质期只有几个月，而**决策框架**的保质期长得多。所有「某引擎更好」的表述都绑定具体场景；所有数据都标注了时效。落地前请以你候选引擎当前版本的官方文档与 release notes 复核（截至 2026 年 9 月）。

## 14.1 vLLM vs SGLang 深度对比

![vLLM 偏吞吐、SGLang 偏低延迟：谁更合适，取决于你的负载压在哪一头](./assets/ch14-comparison-scales.png)

### 14.1.1 架构层：两条技术路线的对照

| 维度 | vLLM | SGLang | 工程含义 |
|---|---|---|---|
| 内存管理 | PagedAttention：分页式 KV 池（OS 页表思路） | RadixAttention：基数树共享 KV（前缀树思路） | PagedAttention 管理的是「单请求内」的碎片；RadixAttention 额外管「跨请求」的复用。前缀复用上 SGLang 是原生设计，vLLM 以 APC（prefix caching）补齐（2.3–4.4 节） |
| 调度器 | V1 统一调度器（5.3 节）：去掉 prefill/decode 硬区分、Persistent Batch | 零开销调度器（5.4 节）：Overlap Scheduling + CUDA Graph Runner + Rust API 层 | 两者都已把「调度开销」压到很低，差异更多在**调度的可编程性**与生态习惯 |
| 投机解码 | 配置式（第 7 章）：n-gram / EAGLE / MTP 等，参数开关 | Spec V2 统一框架（5.x / 10.x）：自回归起草 + 并行起草（DFlash/DSpark） | 能力趋同，配置形态不同；新方法的支持节奏两边都很勤 |
| 结构化输出 | xgrammar / guided decoding 后端 | xgrammar 同站 + 压缩 FSM / jump-forward + DSL 控制流（12.2 节） | 复杂多分支结构化任务（多 schema 跳转、正则约束）SGLang 的表达力更强 |

**一句话概括架构分歧**：vLLM 把功夫花在「把通用引擎做到极致稳」；SGLang 把功夫花在「让复用与控制流成为一等公民」。这不是优劣，是两条路线。

### 14.1.2 能力层：按维度打分（定性，以 2026-09 公开资料为准）

| 能力维度 | vLLM | SGLang | 备注 |
|---|---|---|---|
| 模型覆盖广度 | ★★★★★ | ★★★★☆ | vLLM 支持列表最广，长尾模型多 |
| 量化支持广度 | ★★★★★ | ★★★★☆ | vLLM 生态对 AWQ/GPTQ/FP8/PTP 系列集成最全 |
| 新架构 Day-0 | ★★★★ | ★★★★★ | DeepSeek 系、混合注意力、稀疏注意力常 SGLang 先合入（12.3 节） |
| 超大 MoE / MLA / EP | ★★★★ | ★★★★★ | DeepSeek 级模型 SGLang 是事实上的首选（12.3 节） |
| 前缀复用与路由 | ★★★★ | ★★★★★ | RadixAttention + Router 原生（12.4 节） |
| PD 分离成熟度 | ★★★★ | ★★★★★ | 两侧都在快速迭代（第 13 章），SGLang 的分离形态更早经生产验证 |
| 硬件后端广度 | ★★★★★ | ★★★★ | vLLM 的 CPU/TPU/各种 NPU 后端更多（14.3 节） |
| 社区规模与资料 | ★★★★★ | ★★★★☆ | vLLM 的教程、issue 库、问答覆盖更厚 |

### 14.1.3 工程层与性能层

**工程层**关注的四件事：

- **发版节奏**：两个引擎都处于「双周一小版、每月一大版」的高频迭代期。生产部署**锁版本 + 订阅 release notes** 是纪律（第 20 章的部署形态天然支持版本灰度）。
- **API 稳定性**：两边的 Python API 与 CLI 参数都仍有 breaking change（尤其投机解码、PD 分离、量化相关参数）。台账（10.1 节）里记录参数快照，迁移成本才可控。
- **运维生态**：K8s Operator、监控指标、bench 工具两边都齐（11、12 章）；vLLM 的资料面更广，SGLang 的 DeepSeek 系实战资料更密。
- **人才市场**：两个都懂是 2026 年推理工程师的基本盘；团队既有经验是选型的合法加权项——**会用的引擎 + 做对的调优，常胜过换一个「理论上更快」的引擎**。

**性能层**的立场（呼应 9 章开篇）：

> 不给「谁更快」的结论，给「什么负载谁占优」：

| 负载形态 | 占优倾向 | 原因 |
|---|---|---|
| 高前缀相似度（多轮对话 / RAG / 批量同模板） | SGLang 略优 | RadixAttention 原生复用 + Router 聚合（9.1/9.4） |
| DeepSeek 级超大 MoE / 长上下文旗舰模型 | SGLang 略优 | MLA + EP + 分离架构的工程成熟度（9.3） |
| 长尾模型 / 多模型混布 / 极致量化 | vLLM 略优 | 模型覆盖与量化生态最广 |
| 标准 7B–32B 稠密模型、通用服务 | 基本打平 | 调度都已零开销化，差异被调优空间淹没 |

**「基本打平」是重要结论**：对多数中小模型场景，第 10 章调优做到位带来的收益，远大于换引擎。先调优，再谈换。

### 14.1.4 选型决策表

| 你的场景 | 推荐 | 理由 |
|---|---|---|
| DeepSeek / Kimi 级超大 MoE，或 MLA / 混合注意力新架构 | SGLang | Day-0 与 EP/MLA/分离的成熟度（9.3） |
| 服务以多轮对话 / RAG 为主，前缀相似度高 | SGLang（或 vLLM + 强缓存路由） | 前缀复用是核心收益 |
| 多长尾模型、多量化变体、多硬件后端 | vLLM | 覆盖广度第一 |
| 已有 vLLM 生产集群，无 SGLang 强需求 | **不换** | 迁移成本 > 收益（7 章/13 章的调优先做满） |
| 团队从零开始，两者皆无经验 | vLLM 起步 | 资料多、坑有人踩过；跑通后再评估 |
| 需要 DSL 式多分支结构化生成 | SGLang | FSM + 控制流融合（9.2） |
| RL rollout 后训练 | SGLang 优先，vLLM 亦可 | 权重热更新 / sleep mode 协同更成熟（9.5/10 章） |

## 14.2 与其他引擎横向对比

| 引擎 | 定位 | 强项 | 弱项 | 什么时候选它 |
|---|---|---|---|---|
| **TensorRT-LLM** | NVIDIA 官方极限优化引擎 | 单卡/单模型极致性能（kernel 级优化、编译期融合）；TRT 生态 | 模型支持滞后于 vLLM/SGLang；构建/调参复杂度高；迭代绑定 NVIDIA 节奏 | 性能榨到极限是硬需求（高价值、负载稳定的明星模型）；团队有 TRT 经验 |
| **LMDeploy**（上海 AI Lab） | 国产生态友好、TurboMind 后端 | 国产模型（InternLM 系等）适配好；部署轻量；量化（W4A16 等）实用 | 国际社区与模型覆盖弱于 vLLM | 以国产模型为主、追求轻量部署 |
| **TGI**（HuggingFace） | 早期的服务化标杆 | 与 HF 生态集成 | 官方维护重心转移、创新节奏放缓（社区普遍观察） | 已有 TGI 存量且运行稳定——**新项目不建议首选** |
| **Ollama / llama.cpp** | 本地 / 边缘 | 零门槛、跨平台（甚至 CPU/Mac）、GGUF 量化生态 | 吞吐与并发能力不面向高 QPS 服务 | 个人开发、本地演示、边缘设备；**不是**生产集群选项 |
| **ktransformers / ik_llama.cpp** 等社区引擎 | 单机大模型（消费级硬件跑 MoE） | 显存不够内存凑的极限玩法 | 生产特性（监控/多副本/调度）缺失 | 个人工作站跑满血 MoE 做研究 |

**什么时候该换引擎**（从现有引擎迁出的判据，按顺序自检）：

1. 现引擎**确实**无法满足 SLO（11 章 Goodput 验证过，不是「感觉慢」）；
2. 目标引擎在你负载上的**压测收益 > 30%**（低于此，迁移与回归测试成本不划算）;
3. 目标引擎的能力不依赖你团队没有的稀缺技能（如 TRT-LLM 的构建调参）;
4. 有 1–2 周的回归窗口（质量评估 + 性能压测 + 灰度，12.3.4）。

四条全过才换。**换引擎是最后手段，前面还有参数调优（第 10 章）、并行策略（第 6 章）、PD 分离（第 13 章）三道更便宜的杠杆。**

## 14.3 国产化硬件适配 ⏭️

> 本节是 2026-09 的快照，国产硬件后端迭代极快，数据请以各项目当前文档为准。

| 硬件 | 推理引擎支持现状 | 能力差异要点 | 迁移成本 |
|---|---|---|---|
| **昇腾 NPU**（华为） | vLLM Ascend（官方维护的插件后端）、MindIE、SGLang 昇腾适配 | 主流模型覆盖较全；性能与 CUDA 旗舰卡仍有差距，迭代快 | 低–中：vLLM 代码几乎零改动，换镜像 + 环境变量；算子级差异需回归 |
| **摩尔线程 MUSA** | 官方 fork vLLM 适配 | 常用模型可用；新特性跟进有滞后 | 中：参数与算子差异需逐项验证 |
| **寒武纪** | 思元系列有引擎适配 | 生态相对封闭，依赖厂商工具链 | 中–高：通常绑定厂商推理栈 |
| **海光 DCU** | 兼容 ROCm 路线，vLLM/引擎可跑 | 与 AMD 生态同源 | 中：按 ROCm 经验迁移 |

**给选型者的三条判断**：

1. **先确认模型再确认引擎**：国产硬件上「某个模型能不能跑」比「哪个引擎快」更优先——先查该后端的模型支持列表，再谈性能。
2. **量化与投机是后进能力**：国产后端对 FP8 KV、投机解码等新能力的支持普遍晚于 CUDA 主线，容量规划时不要按 CUDA 旗舰卡的能力做预算（第 4 章公式仍适用，但「可用的优化选项」变少）。
3. **混合集群是常态**：国产化替代常按「批次」推进，架构上（第 20 章）把「引擎镜像 + 权重缓存」做成与硬件无关的层，多硬件池共存才不痛苦。

## 14.4 选型决策树

![选型不是「选更好的」，而是按自己的负载走一条决策路径](./assets/ch14-decision-tree.png)

四要素：**模型 + 硬件 + 负载 + 团队**。按顺序问，每个问题都有唯一出口：

```
Q1 模型是什么？
├─ 超大 MoE / MLA / 混合注意力旗舰（DeepSeek 系、Kimi 等）
│    → SGLang 优先（9.3）；确认硬件满足（多机 EP + 高速互联）
├─ 主流稠密 7B–32B（Qwen / Llama 系）
│    → 进 Q2
└─ 长尾 / 自研 / 多模态特殊模型
     → 查 vLLM 支持列表（最广）；不支持则找该模型的官方推荐引擎

Q2 硬件是什么？
├─ NVIDIA 主力卡（A100/H100/H20/4090 等）
│    → 进 Q3
├─ 国产 NPU/DCU（14.3）
│    → 先查模型支持列表 → vLLM Ascend 等插件后端起步
└─ Mac / 纯 CPU / 消费级小显存
     → llama.cpp / Ollama（非生产）；生产另议预算

Q3 负载是什么形态？
├─ 前缀相似度高（多轮/RAG/同模板批处理）且规模大
│    → SGLang（Radix + Router）；或 vLLM + APC + 缓存路由
├─ 前缀随机、吞吐型离线批处理
│    → 两者皆可；离线场景用 offline batch（第 6/9 章），选熟悉的
├─ 极低延迟硬需求、负载稳定、模型固定
│    → 评估 TensorRT-LLM（先过 14.2 的换引擎四判据）
└─ 高并发在线服务 + 成本敏感
    → 两者皆可起步；用第 10 章方法压测对比，谁 Goodput 高用谁

Q4 团队是什么状态？
├─ 已有某引擎生产经验
│    → 沿用 + 调优到位（第 10 章），除非 14.1.4 表明确命中对方强项
└─ 从零开始
     → vLLM 起步（资料与坑位覆盖最厚），场景命中 SGLang 强项时并行试点
```

**使用说明**：决策树给出的是「默认起点」，不是终审。任何起点确定后，用第 13 章的压测方法做一轮验收——**决策树的终点是 Goodput 数字，不是引擎名**。

## 14.5 技术趋势判断

基于 2025–2026 的公开演进，给出四条判断（⚠️ 判断有保质期，仅代表写作时点）：

1. **引擎层的能力在趋同，编排层在分化**。调度、投机、量化、前缀缓存这些「单引擎内」的能力，两个主流引擎你追我赶，差异窗口越来越短；而 **PD 分离编排、KV 集群级管理、SLO 驱动路由**等「跨引擎/跨节点」的能力（NVIDIA Dynamo、llm-d 等）正在成为新的竞争层级。**关注编排层的演进，比追引擎小版本更有长期价值**（第 11/13 章的架构形态会因此继续演化）。

2. **模型架构的迭代速度 > 引擎适配速度**。混合注意力、稀疏注意力、MTP 等（4.8 节）意味着「新模型发布 → 引擎完整支持 → 性能调优到位」有数周到数月的 lag。**生产选模型时预留这个 lag**，追新要付出适配成本。

3. **推理与训练的边界在模糊**。RL rollout（9.5/10 章）、权重热更新、sleep mode——推理引擎正在成为训练管线的一等组件。「推理工程师」的技能栈正在向「推理 + 分布式训练协同」扩展。

4. **Agent 负载在重写容量假设**。多轮长上下文、会话级 KV 复用、突发到达——第 19 章 19.1 节的负载建模问题会越来越尖锐。**KV 命中率正在从「优化项」变成「成本模型的核心变量」**。

## 本章小结

1. **vLLM vs SGLang 是两条路线**：vLLM 把通用引擎做到极致稳（覆盖广、量化全、资料厚），SGLang 让复用与控制流成为一等公民（Radix 原生、Day-0 快、超大 MoE 成熟）。选型绑定场景，不谈「谁更快」。
2. **多数中小模型场景两者基本打平**——第 10 章的调优收益远大于换引擎收益。换引擎的判据（14.2）：Goodput 验证不达标 + 压测收益 > 30% + 技能可得 + 回归窗口充足，四条全过才换。
3. **其他引擎各就各位**：TRT-LLM 是明星模型的极限性能选项，LMDeploy 是国产模型轻量选项，TGI 存量维持，Ollama/llama.cpp 是本地与边缘。
4. **国产硬件先查模型支持列表**，再谈性能与引擎；量化/投机等新能力普遍滞后，容量规划按「可用优化变少」做预算。
5. **决策树四问**：模型 → 硬件 → 负载 → 团队，终点是 Goodput 数字而非引擎名。
6. **四条趋势**：编排层在分化（值得长期关注）、模型快于引擎（预留适配 lag）、推理训练边界模糊（rollout 技能）、Agent 负载重写容量假设（KV 命中率进入成本模型）。
